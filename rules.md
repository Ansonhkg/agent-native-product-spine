# Architecture rules

All rules are active. Conditional rules become mandatory when their capability exists. The host is the authoritative application runtime, not necessarily a separate server or a specific deployment technology.

| ID | Applies to | Requirement | Verification |
| --- | --- | --- | --- |
| ARCH-001 | Every product operation | One application execution path. UI, HTTP, CLI, MCP, and other supported adapters resolve to the same operation/service. Catalog metadata never executes domain logic. | Trace callers to shared dispatch; reject alternate business logic and direct adapter-to-store writes. |
| ARCH-002 | Authoritative product state | Host owns authentication, capabilities, resource scope, validation, persistence, and activation. Client input cannot establish authority. Secrets stay behind the host boundary. | Denied-capability, cross-scope, and secret-exposure checks. For browser-only apps, document that browser storage and permissions are not a server security boundary. |
| ARCH-003 | Every operation | Stable IDs, input/output/error contracts, mutation classification, scope requirements, surface eligibility, and canonical bindings. Discovery is filtered by caller permissions. | Schema validation, unique IDs/bindings, route round-trip checks, handler coverage, and filtered discovery. |
| ARCH-004 | Every product mutation | Explicit workflow with at least validate → persist. Commit related state, audit, and applicable receipt/outbox records atomically. Check revisions and mutable authority at commit, including grant revocation and removed-resource identity. | Conflicting writes, stale code/data snapshots, revocation races, and transaction rollback checks. External effects require provider idempotency or a separate protocol; do not claim database atomicity covers them. |
| ARCH-005 | Effectful application logic | Use Effect major version 4 with typed services/errors and explicit execution boundaries. Adapt third-party Promises at integration boundaries. Pure utilities remain ordinary code. | Resolved dependency versions, typed failure paths, shared runtime wiring, and cleanup checks. Verify APIs against the installed v4 types. |
| ARCH-006 | Client server state | Use the appropriate TanStack Query framework adapter. Stable client, complete query keys, cache ownership, mutation updates, and query cancellation. Every product UI domain observes writes from other interfaces without manual refresh. | CLI/MCP/other-client mutation while UI is open; expected state arrives without duplicate application. Avoid competing caches and multiplying retries. |
| ARCH-007 | Multi-step or long-running execution; durable execution when work must survive interruption | Explicit versioned workflow definition, guarded transitions, bounded concurrency, cancellation that waits for cleanup, and declared restart/retry behavior. Use Pi Durable with persistent storage for workflows that must survive process crashes, restarts, or application closure. Commit task intent and checkpoints; declare safe replay, reconciliation, or explicit interruption for each effect. Definition identity is pinned to each run; retain compatible code for unfinished runs rather than replacing it silently. | Illegal transitions, interruption, cleanup, partial completion, and restart checks. Kill and reopen the process; verify task identity, committed progress, replay policy, and no duplicate protected effects. Ordinary retries, memory storage, or persistence of status alone do not prove durable recovery. |
| ARCH-008 | Execution telemetry and visualizations | Emit structured events with operation/run/step identities and timestamps. Graphs derive from executable definitions; timelines derive from observed events. Record attempts separately. | Definition/event consistency. Phase entry cannot masquerade as successful completion. No model-prose parsing to invent execution history. |
| ARCH-009 | Untrusted executable extensions | Isolate execution with explicit resource limits and scoped host bridges. Extensions propose validated changes rather than acquiring unrestricted persistence, network, credentials, or host filesystem access. | Escape/unauthorized-access rejection, read-only write rejection, limits, cancellation, and output validation. Ordinary trusted services do not require a sandbox. |
| ARCH-010 | Versioned executable artifacts | Immutable candidate → syntax/schema/compatibility checks → declared evaluation → atomic activation against checked revisions. Explicit approval only where product policy requires it. Rollback restores compatible code, not historical data. | Failed evaluation never activates; concurrent removal/change wins; activation metadata stays consistent; rollback compatibility checks. |
| ARCH-011 | Background/cross-app delivery | Commit pending delivery with source state. Pin delivery contract/version, scope grants narrowly, and atomically commit receipt with target mutation. Define retry, revocation, ordering, and cycle policies. | Lost acknowledgement replay, duplicate delivery, revoked connection, and forbidden-cycle checks. No exactly-once external-effects claim without supporting evidence. |
| ARCH-012 | Every app | Independent action inventory and declared conformance profile. Every required action/surface/check needs fresh executable evidence. New apps have zero debt; existing apps ratchet exact inherited gaps. | Inventory reconciliation, structural gate, behavioral results, immutable HTML/JSON runs, and no new/stale baseline entries. Never infer coverage from imports, handler presence, or generated declarations. |
| ARCH-013 | Every app | Provide a discoverable API documentation page and `/llms.txt`. Derive operation/tool references and machine exports from canonical contracts. Document all supported agent interfaces, connection/authentication, scope, schemas, errors, mutation/retry semantics, and examples. Follow documentation.md; documentation is part of the shipped product. | Reconcile docs against runtime bindings/discovery, validate schemas and examples, fetch docs/llms.txt and check links/content types, and verify authorization-safe exposure. Missing or stale docs fail conformance. |
| ARCH-014 | Application navigation and deep links | Use slash-separated URL paths for pages, resource identity/scope, tabs, and documentation references. Do not encode navigation in `#` fragments or `?` query parameters. Use client-side routing; direct navigation, reload, and browser Back/Forward must restore the addressed view. Transport query parameters for API inputs or external protocols are outside this navigation rule. | Reconcile links and route definitions with the navigation inventory; assert canonical navigation URLs have empty search/hash, route values round-trip safely, and direct load, reload, and Back/Forward restore the same view. |

Beyond the explicit stack requirements in ARCH-005, ARCH-006, and ARCH-007, do not hard-code a framework's folder names, a database, runtime, hosting vendor, evaluator, or layout as an architectural requirement. Ports describe infrastructure needs; adapters supply them. Choose compatible implementations for the app while preserving these guarantees.
